3 The pattern
Five patterns to preserve
Consistency, already earned.
Five patterns across Field Type Selection and the Settings Screen already work the way they should — proof the team understands the problem. Level 1 leaves them alone and builds the rest to match.
The Settings Screen already treats AI as a mode
The Fill method switcher models AI as a property of a data type, not a separate kind of field. This is the mental model Level 1 protects — and extends onto the Type Selection Screen (where it currently doesn't apply).
Template dropdown is consistent within each field type
Long Text: same 5 templates (Custom Instructions, Summary, Translation, Action Items, Progress Updates) in the same order across entries. Dropdown: same 4 (Sentiment, Categorize, T-shirt Size, Custom). Within-field-type consistency is a win worth protecting.
Brain icon on "Fill with AI"
Consistent purple Brain sparkle across every entry point. The visual language for ClickUp Brain already exists — Level 1's Brain-branding work extends this asset, it doesn't invent one.
CFM's Button handling is the reference pattern
Button is greyed out at selection with an explanatory tooltip ("Buttons can be created at the Space, Folder, or List level.") — exactly how a scope-limited field should be clearly indicated. T3 asks Task to adopt this pattern; the pattern already exists.
The shared underlying component already exists
The three variants already share an underlying component in code — they just diverge at the presentation layer. The unification work doesn't require rebuilding anything. It requires enforcing the shared component as the source of truth. Small effort. Large impact.

One screen → one story → one fix.

L1 unifies what already exists: three variants of one component, one screen with fifty renderings — collapsed into a single coordinated form. Most findings are code-level and a copy pass.
